# PICO Security & Risk Register

## 1. Local Development Trust Boundary

In local development:
- **Local Machine Boundary**: The host environment (Windows laptop, local filesystem, Ollama instance) is the core trust zone.
- **Client/Browser Boundary**: Web UI or IPC clients run in an untrusted or semi-trusted context. Server-side secrets, database connection credentials, and provider API keys MUST NEVER be passed to client-side bundles or HTTP responses.
- **Model Provider Boundary**:
  - Local inference (Ollama running `qwen3.5:2b` or `qwen3.5:4b`) remains entirely inside the machine's loopback network interface (`127.0.0.1`).
  - Cloud inference (Anthropic, OpenAI, Gemini) crosses the external perimeter and transmits prompts over TLS. Under no circumstance may context classified as `SECRET`, `SENSITIVE`, or `INTERNAL` cross this boundary. Only purely `PUBLIC` effective context is eligible for cloud transmission, and only when cloud access is explicitly enabled (`CLOUD_ENABLED=true`). There is no sensitive-data consent exception in the current policy.
- **Untrusted Ingestion Boundary**: Any external content (web scrape, email, file dropped into workspace, API output) is treated as potentially malicious and isolated from system prompts.

## 3. Safeguards Required Before Real External Actions

Before PICO is authorized to execute real external actions (file writing outside sandbox, sending emails, physical home actuation, invoking cloud APIs):
1. **Sandboxing**: Filesystem operations restricted to explicit target directory paths; paths containing `..` or targeting system directories are rejected.
2. **Interactive Confirmation**: Destructive tools and physical actuation trigger a mandatory approval ticket with the exact payload diff and canonical SHA-256 digest displayed to the user.
3. **Execution Ledger**: Every action must be recorded to the ledger with an idempotency key before execution begins.
4. **Offline Capability Test**: System must pass the offline test suite confirming all core local features work without internet connectivity.
5. **Physical Actuation Safety Gate (Milestone P7.3)**:
   - Actuation strictly gated by `HOME_ASSISTANT_ACTUATION_ENABLED=true` and explicit test light entity configuration.
   - Bounded to `turn_on` and `turn_off` on the single designated light; `toggle` and all other domains are blocked.
   - Triple-digest validation recomputed immediately before dispatch.
   - Single-use approval ticket consumed atomically on dispatch.
   - Independent read-only verification required to declare success; zero automatic retries on dispatch uncertainty.
   - All automated test runs execute against synthetic mock transports without touching physical devices.
6. **Desktop Application Launch Safety Gate (Milestone P8.1)**:
   - Application launching strictly gated by server-side allowlist (`OS_APPLICATION_ALLOWLIST`), empty by default.
   - Shells, interpreters, and scripts prohibited from allowlist; direct binary executables (`.exe`) with `shell=False` only.
   - Child process environment stripped of all PICO secrets, approval tokens, and integration credentials.
   - Mandatory human operator approval bound to SHA-256 canonical digest; single-use ticket consumed atomically.
   - Launch Profile Fingerprint Binding: Approval cryptographically binds canonical launch profile fingerprint (alias, executable, args, working directory); re-verified at execution boundary so any post-approval allowlist mutation fails closed with zero process creation.
   - Distinct honest verification statuses; zero automatic retries on launch failure or uncertainty.
   - Automated tests execute exclusively against synthetic fake adapters without launching real desktop processes in CI.
7. **Filesystem Modification Safety Gate (Milestone P8.2 & Follow-up Hardening)**:
   - Server-configured filesystem root allowlist (`PICO_FILESYSTEM_ALLOWED_ROOTS`), strictly empty by default.
   - Operations strictly bounded to `create` (new text file, parent directory exists, target absent) and `replace` (existing text file).
   - Fail-Closed Permissions: Write operations (`filesystem:write`) for both apply and rollback strictly require a non-empty server-side `APPROVAL_SECRET_TOKEN` and constant-time match (`secrets.compare_digest`). Unset secret, missing token, or mismatched token fails closed with zero mutations.
   - Windows Handle Boundary & Directory Hierarchy Pinning: During reads, mutations, deletions, and rollback, PICO pins every directory from the configured root down to the target parent using `CreateFileW` with `FILE_LIST_DIRECTORY`, `FILE_FLAG_BACKUP_SEMANTICS | FILE_FLAG_OPEN_REPARSE_POINT`, and `FILE_SHARE_READ | FILE_SHARE_WRITE` (omitting `FILE_SHARE_DELETE`). The Windows NT kernel blocks any attempt by external processes to delete, rename, or swap pinned directories with junctions (`WinError 32: ERROR_SHARING_VIOLATION`).
   - Reparse Inspection & Fail-Closed Errors: All handles and path components are inspected for `FILE_ATTRIBUTE_REPARSE_POINT` and verified via `GetFinalPathNameByHandleW`. Filesystem inspection errors (e.g., `PermissionError` or uncertain OS errors) fail closed (`ValidationError`), treating any inaccessible or uncertain path component as unsafe.
   - Exclusive Creation (`CREATE_NEW`): Kernel-enforced atomic creation for new files within pinned directory hierarchy, guaranteeing existing or concurrently created files cannot be overwritten.
   - Handle-Based Rollback Deletion: Rollback deletions open target files with `DELETE | FILE_READ_DATA | FILE_FLAG_OPEN_REPARSE_POINT`, verify file identity and expected digest on the handle, and issue deletion via `SetFileInformationByHandle(FileDispositionInfo, True)`. Deletion is bound directly to the verified filesystem object, preventing redirected deletions outside the allowlisted root.
   - Safe Temporary File Cleanup: `safe_unlink` uses handle inspection to ensure temporary staging files (`.pico_tmp_*`) are never deleted if redirected to symlinks, junctions, or files outside the authorized root.
    - Honest Operational Replacement Semantics: On Windows NTFS, atomic target-bound replacement is guaranteed by opening the target file exclusively with `GENERIC_READ | DELETE` and `FILE_SHARE_READ` (omitting `FILE_SHARE_WRITE` and `FILE_SHARE_DELETE`) so no external process can modify, rename, delete, or replace the approved target while attributes and expected digest are validated; staging replacement content into an open temporary file handle (`h_temp`, `.pico_tmp_*`) via `CREATE_NEW` with `GENERIC_READ | GENERIC_WRITE | DELETE` and `FILE_SHARE_READ` in the pinned parent directory; relocating the verified target via its open handle using `SetFileInformationByHandle(FileRenameInfo)` to a unique backup file (`.pico_backup_*`); and renaming the open temporary handle `h_temp` directly to the target path using `SetFileInformationByHandle(FileRenameInfo)` with `ReplaceIfExists = False`. Because `h_temp` remains open with exclusive sharing throughout staging and relocation, external processes cannot substitute, overwrite, rename, or unlink the temporary file. If a competing process created or substituted a file at the target path in the relocation window, `SetFileInformationByHandle` fails closed (`ERROR_ALREADY_EXISTS`), marking `h_temp` for disposition and closing it, leaving the competitor file 100% untouched and preserving the displaced original file in the backup path with zero overwrite. The original backup file (`.pico_backup_*`) is preserved until independent post-write handle verification (`h_post`) passes; if verification or cleanup encounters a conflict, the backup is preserved on disk for recovery, the proposal remains `staged`, and the failure is recorded in the execution result and audit ledger. On non-Windows platforms lacking Windows NT kernel handle sharing and directory pinning semantics, atomic filesystem mutations fail closed (`ExecutionError`). Zero automatic retries.
   - Bounded UTF-8 text contract: max 256 KB file size, max 4096 char line length, max 256 KB diff size, rejection of NUL bytes and binary content, LF newline normalization.
   - Proposal & diff staging: inspectable unified diff, original SHA-256 (`ABSENT` or content hash), proposed SHA-256, diff SHA-256 stored in durable local entity (`StagedDiff`).
   - Human operator approval bound to cryptographic `input_digest` via `prepare_input` hook. Any tampering after approval fails closed at dispatch.
   - Independent verification: target is re-opened, read back, and hash-verified against approved proposed content before declaring success. Zero automatic retries.
   - Platform limitations & CI testing: Non-elevated Windows environments cannot create symlinks without developer mode privileges (WinError 1314); tests use verified directory junctions (`_winapi.CreateJunction`) on disk and controlled adapter/OS API mocks for file symlinks. Automated tests execute exclusively inside pytest temporary workspaces (`tmp_path`) with zero modifications to the host or repository filesystem.
8. **Sandboxed Browser Automation Safety Gate (Milestone P8.3)**:
   - Browser automation disabled by default (`BROWSER_AUTOMATION_ENABLED=false`).
   - Server-side origin allowlist (`BROWSER_ALLOWED_ORIGINS=[]`) empty by default; wildcards strictly prohibited.
   - Initial navigation, redirects, and subresources must match the server allowlist and pass SSRF destination filters against loopback, private ranges, link-local, and cloud metadata.
