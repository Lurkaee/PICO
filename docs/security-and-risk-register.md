# PICO Security & Risk Register

## 1. Local Development Trust Boundary

In local development:
- **Local Machine Boundary**: The host environment (Windows laptop, local filesystem, Ollama instance) is the core trust zone.
- **Client/Browser Boundary**: Web UI or IPC clients run in an untrusted or semi-trusted context. Server-side secrets, database connection credentials, and provider API keys MUST NEVER be passed to client-side bundles or HTTP responses.
- **Model Provider Boundary**:
  - Local inference (Ollama running `qwen3.5:2b` or `qwen3.5:4b`) remains entirely inside the machine's loopback network interface (`127.0.0.1`).
  - Cloud inference (Anthropic, OpenAI, Gemini) crosses the external perimeter and transmits prompts over TLS. Under no circumstance may context classified as `SECRET`, `SENSITIVE`, or `INTERNAL` cross this boundary. Only purely `PUBLIC` effective context is eligible for cloud transmission, and only when cloud access is explicitly enabled (`CLOUD_ENABLED=true`). There is no sensitive-data consent exception in the current policy.
- **Untrusted Ingestion Boundary**: Any external content (web scrape, email, file dropped into workspace, API output) is treated as potentially malicious and isolated from system prompts.

## 2. Risk Matrix & Mitigation Strategies

| ID | Threat / Failure Mode | Severity | Impact | Mitigation Strategy |
|---|---|---|---|---|
| **SEC-01** | **Secret Leakage** | Critical | Cloud keys, tokens, or private credentials leaked to model or browser | 1. Environment secrets stored exclusively in server-side configuration (`.env` not in git).<br>2. Context compiler scrubs potential secret patterns before prompt assembly.<br>3. Automated test suite verifies zero secrets in API responses. |
| **SEC-02** | **Prompt Injection (Direct & Indirect)** | High | Untrusted web/document data overrides system instructions or hijacks tool execution | 1. Strict delimiter encapsulation separating system instructions from untrusted data.<br>2. Untrusted inputs tagged as unprivileged context; model outputs evaluated as untrusted proposals.<br>3. Tool execution verified independently. |
| **SEC-03** | **Data-Classification Violations** | Critical | Sensitive, Internal, or Secret user data transmitted to external cloud providers | 1. Mandatory `data_classification` tag on every message and context chunk (`PUBLIC`, `INTERNAL`, `SENSITIVE`, `SECRET`).<br>2. Fail-closed deterministic context policy: effective classification computed across assembled history + prompt; any non-`PUBLIC` item pins request locally (`RULE_PRIVATE_LOCAL_PIN`).<br>3. Zero non-`PUBLIC` content transmitted to cloud inference. Interactive sensitive consent deferred until a separate, tested approval engine is implemented.<br>4. Defense-in-depth check in cloud provider and streaming endpoint. |
| **SEC-04** | **Unauthorized Tool Calls** | Critical | Model executes unintended shell commands, file deletions, or network requests | 1. Strict allowlist tool registry with explicit JSON schemas.<br>2. No arbitrary code execution or unvalidated shell access.<br>3. Policy engine intercepts destructive operations (`write`, `delete`, `send`) requiring explicit user approval. |
| **SEC-05** | **Sensory Eavesdropping & Data Buffer Leakage** | Critical | Microphone or camera continuously records in background; raw audio PCM or video frames persist to disk | 1. Push-to-talk mandatory default: microphone capture requires explicit user consent session (`user_consent=True`); no always-on recording.<br>2. Cameras off by default; snapshots require explicit request.<br>3. Zero retention of raw audio/video buffers: `raw_payload_scrubbed=True` enforced; transient buffers discarded immediately after feature extraction.<br>4. Non-`PUBLIC` classification (`INTERNAL`) prevents cloud transmission. |
| **SEC-06** | **Perception-Induced Privilege Elevation** | Critical | Detected motion, presence, or audio transcription directly triggers tool execution without human authorization | 1. Invariant: A perception event NEVER authorizes tool execution.<br>2. Inferred observations remain probabilistic telemetry; any resultant actions must pass the Policy & Approval Engine.<br>3. System instructions and mandatory privacy rules survive prompt budget pressure. |
| **SEC-07** | **Physical Actuator Violation (Read-Only Bypass)** | High | Sensor events attempt to operate physical home switches, doors, or alarms in P6 | 1. P6 perception layer is strictly read-only.<br>2. No actuator capabilities or physical mutations are exposed or executable in P6; physical actuation is strictly deferred to Milestone P7. |
| **SEC-08** | **Smart-Home Credential & Transport Security** | Critical | Long-lived Home Assistant token leaked; SSRF via arbitrary base URL; plaintext transmission | 1. Server-side token storage only (`HOME_ASSISTANT_ACCESS_TOKEN`).<br>2. Base URL validation strictly enforces loopback vs. non-loopback policy: plain HTTP/WS permitted only for loopback; HTTPS/WSS required for non-loopback destinations unless explicitly opted-in via `HOME_ASSISTANT_ALLOW_INSECURE_TRANSPORT=true`.<br>3. Bounded inbound responses (max 2 MB for states, 256 KB for single entity) before JSON parsing into memory.<br>4. `follow_redirects=False` prevents credential forwarding to third parties.<br>5. Zero token exposure in logs, status responses, error envelopes, or capability outputs. |
| **SEC-09** | **Household State Privacy & Actuation Boundary** | High | Smart-home occupancy, locks, or cameras leaked to cloud; unauthorized device toggling | 1. Home Assistant observations classified as `INTERNAL` (or `SENSITIVE` for locks, alarms, cameras, entry points).<br>2. Effective classification computed across all entities contributing to overview summaries.<br>3. Central privacy gate keeps household context strictly local.<br>4. Absolute read-only transport boundary: WebSocket commands strictly allowlisted to `get_states`, `get_config`, `ping`; reserved fields (`id`, `type`, `auth`) cannot be overridden; caller parameter merging eliminated.<br>5. Concurrency serialized under `asyncio.Lock()` to prevent correlation corruption.<br>6. Zero service calls (`call_service`), mutation endpoints, or write capabilities. Physical actuation strictly deferred to P7.3+. |
| **SEC-10** | **Household API Exposure Boundary** | Critical | Sensitive household state (cameras, locks, presence) exposed to remote network clients without authentication | 1. Route-level fail-closed exposure boundary on `/api/homeassistant/*`.<br>2. Local loopback clients (`127.0.0.1`, `::1`, `localhost`) permitted for local operation.<br>3. Remote non-loopback clients require `X-Pico-Approval-Token` header matching server `APPROVAL_SECRET_TOKEN`; unconfigured/invalid tokens rejected with `403 Forbidden`.<br>4. Connector enablement (`HOME_ASSISTANT_ENABLED=true`) is strictly decoupled from network authorization. |
| **SEC-11** | **Physical Actuation Scope Creep & Approval Bypass** | Critical | Unauthorized actuation of household devices, locks, alarms; tampering with action payload after approval | 1. Strict single test light entity constraint: only `HOME_ASSISTANT_P7_TEST_LIGHT_ENTITY_ID` in `light` domain is eligible; all other domains/devices prohibited.<br>2. Explicit opt-in (`HOME_ASSISTANT_ACTUATION_ENABLED=true`).<br>3. Mandatory human operator approval bound to SHA-256 canonical digest.<br>4. Server-verified `APPROVAL_SECRET_TOKEN` required; loopback callers not exempted.<br>5. Triple-digest agreement check immediately before dispatch: recomputed digest, stored digest, and approved digest must all match.<br>6. Single-use approval ticket prevents replay. |
| **SEC-12** | **Dispatch Uncertainty & Blind Mutation Retries** | High | Network timeout or dropped response during physical service call leads to blind retries or false success | 1. Strictly zero automatic retries (`max_retries=0`, `idempotent=False`).<br>2. Single auditable REST mutation dispatch point.<br>3. Independent read-after-write verification via read-only `get_state` polling.<br>4. Failure or timeout reported truthfully without issuing secondary mutations.<br>5. Software verification against mocks explicitly distinguishes from physical device confirmation (`physical_device_connectivity_claimed=false`). |
| **SEC-13** | **Desktop OS Automation Boundary & Allowlist Escape** | Critical | Arbitrary binary execution, shell injection, alias traversal, or credential inheritance in child processes | 1. Application allowlist is strictly empty by default (`OS_APPLICATION_ALLOWLIST='{}'`).<br>2. Fixed Launch Profiles: Maps validated alias (`^[a-zA-Z0-9_\-]+$`) to absolute executable path; path traversal (`..`), relative paths, and env var expansion (`%`, `$`) fail closed.<br>3. Prohibited shells and interpreters: `cmd.exe`, `powershell.exe`, `pwsh.exe`, `bash.exe`, `sh.exe`, `python.exe`, `wscript.exe`, `cscript.exe` strictly blocked from registration.<br>4. Direct argument-list process creation with `shell=False`; constructing shell command strings is strictly prohibited.<br>5. Minimal sanitized child environment: PICO secrets, approval tokens, HA tokens, and credentials are wiped before child process creation (`build_sanitized_environment()`).<br>6. Dedicated permission `os:launch`, high risk tier, single-use human approval ticket bound to input digest.<br>7. Launch Profile Fingerprint Binding: Canonical SHA-256 fingerprint computed across alias, executable path, ordered args, and working directory is bound into input digest at submission; re-verified at execution boundary. Changing allowlist executable path, arguments, working directory, or reloading configuration after approval invalidates execution and results in zero process creation. |
| **SEC-14** | **Window Context Snooping & False Usability Claims** | High | Unbounded window inspection exposes private window titles to cloud; equating process creation with usable application | 1. Window inspection (`os.inspect_windows`) is strictly read-only and non-consequential; dedicated permission `os:inspect`.<br>2. Conservative data classification `INTERNAL` prevents cloud transmission.<br>3. Hard bounds on window count (max 100) and title length (max 512).<br>4. Honest verification statuses: Distinct states for `process_creation_confirmed`, `independent_window_observation_confirmed`, `launch_uncertain`, `launch_failed`; process creation is never equated with desktop usability.<br>5. Strictly zero automatic retries (`max_retries=0`, `idempotent=False`). |
| **SEC-15** | **Filesystem Path Traversal, Reparse Escapes & Arbitrary Overwrites** | Critical | Malicious path parameters traverse outside allowed root, follow symlink/junction escapes, or overwrite arbitrary files | 1. Server-side filesystem root allowlist (`PICO_FILESYSTEM_ALLOWED_ROOTS`), empty by default.<br>2. Canonical absolute path containment validation; rejects traversal (`..`), device paths (`CON`, `NUL`, etc.), alternate separators, and env vars (`%`, `$`).<br>3. Windows reparse point & symlink defense checks target file and all ancestors in the path hierarchy against `FILE_ATTRIBUTE_REPARSE_POINT`.<br>4. Operation restricted to `create` (new text file, parent exists, target absent) and `replace` (existing text file). Directory creation, binary file editing, and file moves are prohibited.<br>5. Bounded text-only contract: UTF-8 only, max file size 256 KB, max line length 4096, max diff 256 KB, rejection of NUL bytes and binary content.<br>6. Dedicated permission `filesystem:write`, `RiskTier.HIGH`, single-use approval ticket bound to `input_digest` (containing operation, root ID, relative path, expected original digest, proposed content digest, diff digest). |
| **SEC-16** | **Filesystem Staging Desynchronization & Unsafe Rollback Overwrites** | High | Post-approval disk mutation, tampered diff proposal, or conflicting external edits during rollback | 1. Pre-dispatch re-verification in `ToolExecutionEngine`: re-verifies root allowlist membership, checks target file on disk against `expected_original_digest`, and checks stored proposed content and diff digests before execution.<br>2. Atomic write semantics: safe temporary file (`.pico_tmp_*`), flush and sync (`os.fsync`), and atomic move (`os.replace`).<br>3. Independent post-write verification: re-opens target file, computes SHA-256 digest, and asserts exact match against approved proposed digest before declaring success.<br>4. Guarded conflict-safe rollback: fails closed if target file no longer matches the post-apply digest (detects external modifications).<br>5. Zero automatic retries (`max_retries=0`, `idempotent=False`). Full audit logging in immutable event ledger without exposing file contents. |
| **REL-01** | **Duplicate Operations After Retries** | Medium | Network or model timeouts trigger duplicate side effects (e.g., duplicated API calls) | 1. Mandatory `idempotency_key` generated per tool execution.<br>2. Execution coordinator caches tool results by idempotency key.<br>3. Duplicate tool invocations return cached result without re-executing. |
| **REL-02** | **Partial Failures & Interrupted Jobs** | High | Multi-step plan crashes midway, leaving inconsistent state | 1. Execution jobs modeled as stateful DAGs in SQLite.<br>2. Each step transition recorded to append-only event ledger.<br>3. Crash recovery engine resumes from the last confirmed checkpoint. |
| **REL-03** | **Conflicting Concurrent Actions** | Medium | Concurrent requests update the same task or project causing race conditions | 1. SQLite WAL mode with immediate transactions for multi-row updates.<br>2. Explicit entity versioning (`updated_at` checks) and repository transaction locks. |
| **MOD-01** | **Incorrect or Stale Memory** | Medium | Memory service retrieves obsolete facts or hallucinated memories | 1. Provenance tracking linking memories to source conversation and timestamp.<br>2. Time-decay weighting on episodic memory.<br>3. Contradiction detection during semantic consolidation. |
| **MOD-02** | **Misleading Model Claims / Hallucinations** | High | Model falsely claims an action was executed when it failed or did not run | 1. Action results are recorded strictly from actual tool execution returns, never model narration.<br>2. Independent Verifier checks tool return against model claims.<br>3. UI clearly distinguishes actual tool logs from model conversational output. |
| **MOD-03** | **Provider Outage & Unexpected Costs** | Medium | Cloud API rate limit, downtime, or runaway token spend | 1. Local-first fallback for routine tasks; app remains fully usable offline.<br>2. Per-task and per-day token budget limits.<br>3. Inspectable routing decision log tracking cost per turn in cents. |

## 3. Safeguards Required Before Real External Actions

Before PICO is authorized to execute real external actions (file writing outside sandbox, sending emails, physical home actuation, invoking cloud APIs):
1. **Sandboxing**: Filesystem operations restricted to explicit target directory paths; paths containing `..` or targeting system directories are rejected.
2. **Interactive Confirmation**: Destructive tools and physical actuation trigger a mandatory approval ticket with the exact payload diff and canonical SHA-256 digest displayed to the user.
3. **Execution Ledger**: Every action must be recorded to the ledger with an idempotency key before execution begins.
4. **Offline Capability Test**: System must pass the offline test suite confirming all core local features work without internet connectivity.
5. **Physical Actuation Safety Gate (Milestone P7.3)**:
   - Actuation strictly gated by `HOME_ASSISTANT_ACTUATION_ENABLED=true` and explicit test light entity configuration.
   - Bounded to `turn_on` and `turn_off` on the single designated light; `toggle` and all other domains are blocked.
   - Triple-digest validation recomputed immediately before dispatch.
   - Single-use approval ticket consumed atomically on dispatch.
   - Independent read-only verification required to declare success; zero automatic retries on dispatch uncertainty.
   - All automated test runs execute against synthetic mock transports without touching physical devices.
6. **Desktop Application Launch Safety Gate (Milestone P8.1)**:
   - Application launching strictly gated by server-side allowlist (`OS_APPLICATION_ALLOWLIST`), empty by default.
   - Shells, interpreters, and scripts prohibited from allowlist; direct binary executables (`.exe`) with `shell=False` only.
   - Child process environment stripped of all PICO secrets, approval tokens, and integration credentials.
   - Mandatory human operator approval bound to SHA-256 canonical digest; single-use ticket consumed atomically.
   - Launch Profile Fingerprint Binding: Approval cryptographically binds canonical launch profile fingerprint (alias, executable, args, working directory); re-verified at execution boundary so any post-approval allowlist mutation fails closed with zero process creation.
   - Distinct honest verification statuses; zero automatic retries on launch failure or uncertainty.
   - Automated tests execute exclusively against synthetic fake adapters without launching real desktop processes in CI.
7. **Filesystem Modification Safety Gate (Milestone P8.2 & Follow-up Hardening)**:
   - Server-configured filesystem root allowlist (`PICO_FILESYSTEM_ALLOWED_ROOTS`), strictly empty by default.
   - Operations strictly bounded to `create` (new text file, parent directory exists, target absent) and `replace` (existing text file).
   - Fail-Closed Permissions: Write operations (`filesystem:write`) for both apply and rollback strictly require a non-empty server-side `APPROVAL_SECRET_TOKEN` and constant-time match (`secrets.compare_digest`). Unset secret, missing token, or mismatched token fails closed with zero mutations.
   - Hard path validation & anti-redirection boundary: Eliminates unvalidated `os.path.realpath()` redirection outside configured roots. Immediate pre-mutation validation (`verify_boundary_and_reparse`) asserts strict commonpath containment and checks target and all ancestor components for symlinks or reparse points (`FILE_ATTRIBUTE_REPARSE_POINT`, 0x400).
   - Exclusive creation (`os.O_CREAT | os.O_EXCL`): Kernel-enforced atomic creation for new files, guaranteeing a concurrently created target cannot be overwritten.
   - Conditional replacement: Pre-mutation state and expected original digest check immediately before staging in directory-local temporary file (`.pico_tmp_*`), flush, and atomic replacement (`os.replace`).
   - Guarded conflict-safe rollback: Safe deletion verifies expected applied digest immediately before unlink and refuses to unlink symlinks/reparse points; replacement rollback restores original bytes with expected-applied digest verification.
   - Bounded UTF-8 text contract: max 256 KB file size, max 4096 char line length, max 256 KB diff size, rejection of NUL bytes and binary content, LF newline normalization.
   - Proposal & diff staging: inspectable unified diff, original SHA-256 (`ABSENT` or content hash), proposed SHA-256, diff SHA-256 stored in durable local entity (`StagedDiff`).
   - Human operator approval bound to cryptographic `input_digest` via `prepare_input` hook. Any tampering after approval fails closed at dispatch.
   - Independent verification: target is re-opened, read back, and hash-verified against approved proposed content before declaring success. Zero automatic retries.
   - Platform limitations & CI testing: On Windows, non-elevated CI environments cannot create file symlinks (WinError 1314), so symlink swap tests utilize controlled adapter/OS API mocks; directory junctions (`_winapi.CreateJunction`) are fully supported and verified live on disk. Automated tests execute exclusively inside pytest temporary workspaces (`tmp_path`) with zero modifications to the host or repository filesystem.
